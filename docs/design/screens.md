# Pantallas → imagen → datos → endpoint → WebSocket → estados

Fuente visual: `design/reference/` (19 imágenes, leídas una sola vez en la Fase 0). Reglas de negocio: `CLAUDE.md`.

**Estado de este documento.** Es un CONTRATO PROPUESTO, PENDIENTE de confirmar fase a fase. Los endpoints y los tipos de WebSocket no existen aún (solo `GET /health`). Los dos primeros eventos globales (`ROUND_ACTIVATED`, `STANDINGS_UPDATED`) y la ruta `/ws` con primer mensaje `AUTH` vienen de la skill `backend-fastapi`; el resto es propuesta mía y se definirá en `backend/app/realtime/events.py` (espejo en `mobile/src/realtime/events.ts`).

## Convenciones

- **Errores REST**: `{"error": {"code": "...", "message": "...", "details": {}}}`. Códigos mencionados abajo: `INVALID_CREDENTIALS`, `EMAIL_TAKEN`, `TOURNAMENT_FULL`, `ALREADY_JOINED`, `REGISTRATION_CLOSED`, `MATCH_NOT_ACTIVE`, `NOT_YOUR_TEAM`, `INVALID_TRANSITION`, `PENDING_EVENTS` (este último solo se usa en cliente para bloquear Finalizar). Cada uno se confirma en su fase.
- **Auth**: todas las rutas salvo `/health`, `/auth/login` y `/auth/register` exigen `Authorization: Bearer <access_token>`. Rol y `user_id` salen de `profiles`, no del cliente.
- **WebSocket**: `/ws`, primer mensaje `{"type":"AUTH","token":"..."}`. El WS solo NOTIFICA: al recibir un evento la app invalida la consulta de TanStack Query correspondiente y vuelve a pedir por REST. Al reconectar, invalida todo lo activo.
- **Estado "offline"** (columna Estados): lectura desde caché persistida de TanStack Query con aviso visible. Las acciones marcadas "solo online" se muestran deshabilitadas con el motivo.
- **Estados comunes** (imagen 15): *carga* = esqueletos; *vacío* = ilustración + texto + acción; *error* = bloque rojo + "REINTENTAR"; *offline* = banner amarillo "Sin conexión / Mostrando datos guardados".
- **Imágenes**: escudos `GET /media/crests/{club_id}`, fotos `GET /media/players/{player_id}`. Placeholder discontinuo mientras cargan o si faltan.

## Mapa de eventos WebSocket (propuesto)

| Tipo | Quién lo recibe | Cuándo | Qué hace la app |
|---|---|---|---|
| `ROUND_ACTIVATED` | Todos | El admin activa una fecha | Invalida calendario, inicio y mi partido |
| `STANDINGS_UPDATED` | Todos | Un partido pasa a CONFIRMED o RESOLVED | Invalida tabla e inicio |
| `MATCH_STATUS_CHANGED` | Los dos participantes del partido (y el admin) | Cambia `matches.status` | Invalida detalle de partido y calendario |
| `MATCH_EVENT_ADDED` | Los dos participantes del partido | Nueva fila en `match_events` | Invalida detalle de partido |
| `MATCH_RESULT_PENDING` | Solo el visitante | El local finaliza (PENDING_CONFIRMATION) | Muestra el modal de confirmar (9B) |

El destinatario lo decide el backend tras buscar los participantes del partido (listener de Supabase Realtime → gestor de conexiones propio). No hay evento de borrado: no hay borrado de eventos en el MVP.
